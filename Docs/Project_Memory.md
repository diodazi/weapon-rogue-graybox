### 2.1 本轮已确认战斗基线

| 类别 | 当前决定 |
|---|---|
| 固定称呼 | 移动、蓄力、轻攻击、跳跃、冲刺、重攻击、刃、柄、弹反、精确弹反、架势条、破势、霸体、连招、派生攻击、蓄力冲刺 |
| 键位 | A/D 左右移动；S 蓄力；J 轻攻击；K 跳跃；L 冲刺；U 重攻击；W 不跳跃，其具体功能待定 |
| 刃柄受击 | 柄额外受伤、刃伤害更低；分区差异只影响 HP，不改变同一普通命中的架势增量；具体轮廓依据图稿 |
| 刃柄进攻 | 多数攻击用刃；只有专门设计的柄端攻击启用柄伤害 |
| 弹反必要条件 | 双方攻击动作、有效窗口及真实刃刃接触；输入正确但没有碰刃不能成功 |
| 精确弹反 | 预判输入稍早于实际碰刃；每个武器动作对齐输入、位移、动画与精确接触窗口；原 1–0 动画示例不是实际固定帧数 |
| 弹反结果 | 成功关系双方不扣 HP，攻击方攻击失效；攻击方架势增长多、防守方少，精确时攻击方额外增加；服从架势锁定 |
| 弹反保护 | 双方极短 HP 保护，短于双方恢复窗口；不免命中架势增长、击退或打断，结束后第三方仍可造成伤害 |
| 附带接近位移 | 只是部分攻击的额外位移；起手取最近敌方的位置，确定方向与距离后不继续追踪；不自动接近队友 |
| 一攻二守 | 分别检查两名防守者；成功者都成功，失败者正常受伤；攻击方弹反架势只增加一次 |
| 二攻一守 | 两个来袭分别判断，防住一组不能自动免除另一组失败结果；两个攻击方各承担自己的结果 |
| 同次交锋顺序 | 收集逐对结果→按既有状态结算失败命中与合并架势→施加本次新弹反保护与后续攻击失效；尊重交锋前已有保护 |
| 多方仍待定 | 交锋分组与时间边界、同时起手先攻方识别、普通／精确混合增量、二攻一守防守方增量合并，不擅自取最大或相加 |
| 普通命中与回落 | 普通命中只微量加架势；无新增压力一段时间后自然回落；具体量、延迟和速率未定 |
| 破势期间 | 玩家和 Boss 均适用；固定时间无法操作，受击增伤、架势锁定；受击不刷新、不延长失控 |
| 破势结束 | 恢复操作、架势清零但继续锁定；经过独立间隔后才重新允许架势增长与回落；不附赠 HP 无敌 |
| 霸体 | 自身攻击不能被弹反；免受击打断、击退和破势；仍掉 HP；架势整体锁定，不增长不回落 |
| 霸体特殊满架势 | 只有显式 Boss／技能规则可作为例外置满，霸体结束后再破势；普通命中不能绕过锁定 |
| 连招与派生 | 连招可由同时或顺序输入触发；派生承接前动作；轻攻击示意链不是所有武器固定段数 |
| 主动取消 | 仅配置窗口内可取消，超过窗口不允许；具体窗口及可转入动作后续实测 |
| 蓄力基础 | 原地按住 S；蓄满前移动／跳跃打断；蓄满后执行当前可用蓄力技能之外的操作清空 |
| 初始强化动作 | 只有蓄力冲刺；必须蓄满、松开 S 前按 L；成功发动消耗本次蓄力 |
| 冲刺保护 | 普通冲刺无无敌；蓄力冲刺开头／结尾无本次保护，中段残影免 HP、命中架势、击退、打断；不自动锁定架势回落 |
| 共享冲刺资源 | 初始及上限均 2 次；普通与蓄力共用；每次有效发动扣 1 次；每次回充恢复 1 次 |
| 暂定数值 | 回充间隔 1.5 秒为 PROVISIONAL；串行／独立计时及起算、重置规则未定 |
| 防重复结算 | 接触事实与结算分开；逐对结果不能被只保留第一个目标的去重吞掉；攻击方弹反架势另行合并 |
| 防冲刺复制 | 有效发动与扣次数一次完成；回充不因重复回调多发；退出残影立即移除该来源保护，不误清其他保护 |
| 最新跳跃要求 | 基础跳跃足以躲过贴地／低位横扫；能否越过目标本体取决于体型；具体轨迹与数值仍待调试 |
| 最新碰撞修订 | 修复背后攻击不易接触；蓄力冲刺残影中段可穿过对方单位，当前代码尚未实现穿身 |
| 最新弹反反馈 | 攻击方明显回弹；防守方短促反震后稳定；加入仅影响双方的短促碰撞停顿，其他单位继续运行 |
| 动作后续 | 优化各武器起手、攻击轨迹、接触反应、派生与收招；正式手绘与依图稿模组继续等待参考 |

这些条目是设计和实现方向的批准记录，不是已经实现或测试通过的声明。所有具体参数参见 GDD 的占位表。

### 2.2 灰盒授权与临时参数

- 使用几何占位形体、临时轮廓和动作验证已确认机制，不因尚无手绘图停止灰盒工作，也不把占位资产作为正式美术定稿。

- 共享冲刺两次等已确认常量保持；1.5 秒回充继续为 `PROVISIONAL`。试验其他值时单独登记，不能据此宣称最终平衡。

## 4. 建议与事实必须分开

本次通过的战斗防重复、多人逐对结算与冲刺生命周期方向已进入第 2.1 节，不再作为未批准建议。该批准不自动覆盖旧文档中无关的大厅或奖励事务建议。

以下均尚未成为用户明确批准的机制，不得在实现汇报中称“用户要求”：

- 大厅任一取消／离区／成员变化时清空所有确认。
- 大厅出界安全回收；场景切换时临时状态和残留攻击物清理的具体策略。
- 大厅练习不产生额外成长收益，以及能量／冷却的重置规则。
- 静止接触、同次刃柄命中优先级、实际多段划分与交锋分组的具体算法；不得把这些细节与已批准的防重复结算方向混为一谈。
- 友伤不产生吸血／击杀收益，反伤不得递归触发等具体触发限制。
- 卡首次生成候选后绑定使用者并锁定；卡片消耗与效果写入原子提交。
- 只有提交选项并写入效果才算用卡；离房清理未提交候选。
- 不足三个合法候选时的退回、放弃或其他兜底方案。
- 单 Boss 固定主视野、先打一件武器样例、隔离测试中重打同 Boss 的验证顺序。

这些建议仍有价值，应在后续大纲修订、实现设计与测试中显式审阅，而非遗漏或偷偷作为既定需求。

## 6. 制作协议

1. 每次迭代先读本文件与 `GDD_MVP.md`。
2. 用户最新明确决定覆盖旧方案；同步更新需求状态与本文件替换表。
3. Loop A 每轮 1–3 个问题；核心机制未闭环前不写文档。
4. Loop B 先提交大纲，必须含两个极端漏洞情景与防范。
